## 3. What is needed to pick back up

Do these first (user actions; each is small):

1. **Restart Claude Code in the project folder** so `env.GH_TOKEN` loads. Until then the agent still uses the broad `gh` keyring login.
2. **Confirm the new token is active:** `gh auth status` should show the fine-grained PAT, and `gh repo view kristiandermody/<some-other-repo>` should fail.
3. **`npx wrangler logout`** to drop the broad Cloudflare OAuth login. Nothing needs it: CI deploys.
4. **Revoke old PATs** on GitHub (Settings, Developer settings, Personal access tokens). An earlier PAT value appeared in the session transcript.
5. **Provide the game spec** (a file in `docs/`, for example `docs/spec.md`, or pasted into chat). The spec has not been shared yet.
6. **Calendar reminders:** roll the Cloudflare CI token before **2027-01-08** (suggest 2026-12-25); GitHub PAT expiry is per its own setting.

Then the agent can start the build. Defaults agreed or proposed (change if wanted):
- Work on feature branches, one small PR per change, never commit to `main`.
- Add a `pull_request` workflow that runs typecheck and tests; only merge when checks are green (`gh pr checks`).
- Proposed: production deploys automatically after staging succeeds on `main`. Currently production is a manual dispatch. This decision is still open.
- Add Playwright e2e tests under `e2e/` and smoke-test the live staging and production URLs with curl (`--http1.1` for WebSocket).
- Follow-up PR: bump `actions/checkout` and `actions/setup-node` (Node 20 deprecation), and note `ubuntu-latest` becomes Ubuntu 26 on 2026-10-19.
- Update the README (it still says "repo structure only").

Known limits to remember:
- Free-plan caps apply to Durable Object requests and duration. Keep WebSocket hibernation. Upgrade to Workers Paid ($5/month) if usage needs it.
- The CI token covers Workers Scripts only. KV, D1 or R2 need new token permissions and the resources created. A new hostname needs Zone: Read plus Workers Routes: Edit on `kristiandermody.com`.
- The auto-mode classifier can block production deploys, PR merges and edits to the agent's own settings. When blocked, the agent stops and reports; the user runs the command or grants a rule.
- `.claude/settings.local.json` contains a live token. It is git-ignored by the user's global ignore file (`~/.config/git/ignore`), not by this repo's `.gitignore`. Do not use `git add -f` on it. Consider also adding it to the repo `.gitignore`.

## 4. Reusable playbook (for other agents building something similar)

Ordered steps to reproduce this setup for a Cloudflare Workers project deployed from GitHub Actions:

1. **Verify the remote and branch state** (`git remote -v`, `git fetch`). An empty remote has no `main`.
2. **Push credentials:** if a push touches `.github/workflows/**`, the token needs the `workflow` scope. Run `gh auth refresh -h github.com -s workflow -c` in a **normal terminal** (it is interactive and times out in a 120 s `!` shell), then `gh auth setup-git` so git uses `gh`'s token instead of a stale keychain PAT.
3. **Check the Cloudflare account yourself, not through a connector.** Confirm the connector's account matches the intended account ID. Check in the dashboard: zone active, DNS has no record for the target hostname, Workers Routes empty, workers.dev subdomain set, plan.
4. **First deploy interactively** (`wrangler login`, then `wrangler deploy --env staging` and `--env production`). Creating a new Worker needs more privilege than updating one, and the custom domain is created at this step.
5. **Then create the CI token** with the minimum permission: Account, Workers Scripts, **Write** (shown as "Edit" in some UIs; the "Legacy, read" row is the wrong one). Account-owned, one account, no zone permissions, 90-day expiry. Add Zone, Workers Routes Edit and Zone Read only if the workflow must add or change routes.
6. **Set the repo secret with stdin, never interactively through a non-TTY shell:** `pbpaste | gh secret set CLOUDFLARE_API_TOKEN --repo OWNER/REPO`. The `!` shell stores an empty secret silently. Verify by running the workflow, since `gh secret list` only shows the name.
7. **Config pitfalls** (see report section 5): declare DO bindings, migrations, assets and routes in each environment; set `routes: []` on staging; set a top-level `name`; use `new_sqlite_classes`; do not leave `.gitkeep` in the assets folder; match `@cloudflare/workers-types` to wrangler's peer range.
8. **Workflow security:** pass `github.event.inputs.*` to scripts through `env:` variables, not directly in `run:`.
9. **Test WebSockets with `curl --http1.1`** and expect HTTP 101.
10. **Agent confinement:** use a fine-grained PAT limited to the single repo (web UI only, no API), put it in the project-local `.claude/settings.local.json` as `env.GH_TOKEN`, deny the Cloudflare MCP connector and destructive commands, and do not give the agent `wrangler deploy`; deploy through CI. The agent cannot write its own permission file under auto mode; the user must invoke `/update-config`.
11. **Loading a token into a file safely:** never paste it into chat. Do not rely on the clipboard staying unchanged while copying a command from chat. Use a script that waits, validates `github_pat_` prefix and length, and refuses anything else. Verify with prefix and length, then a live API call (`gh repo view`), and a negative test against a repo the token must not reach.

Open facts that were not verified: the exact Workers plan (Free is inferred), whether a Worker-scoped Cloudflare token is possible for account-owned tokens in the UI used, and whether the classifier will allow `gh pr merge` and production dispatch once the allow rules are loaded after restart.
